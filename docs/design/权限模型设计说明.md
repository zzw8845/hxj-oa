# 海峡金 OA 权限模型设计说明（定版）

> 整理日期：2026-09-11
> 定位：系统权限底层模型的标准解释文档。任何人问起"部门/角色/人员/岗位/数据范围/权限是什么关系"，指向本文。
> 依据：`docs/design/原型数据清单.md`（纯原型数据）+ 主流产品（钉钉/飞书/泛微/致远/Workday/SAP）行业收敛结构。
> 关联：审批节点配置对照用《原型数据清单》表 3；角色成员对照用其表 1/表 2。

## 一、六个概念的本质

| 概念 | 本质 | 回答的问题 | 落库位置 |
|---|---|---|---|
| **人员** | 授权的主体；档案只记锚点事实（主部门/主岗/主管各一个） | "这是谁" | `sys_user` / `sys_user_department` |
| **部门** | 组织空间；单据的归属地、范围计算的锚点 | "这东西属于哪" | `sys_department` + `sys_department_closure` |
| **岗位** | 职务标签；纯 HR 描述，零授权作用 | "他是干哪行的" | `sys_post`（全局职种库） |
| **角色** | 授权包；系统**唯一**的授权通道 | "他多了一身什么本事" | `sys_role` |
| **数据范围** | 可见宽度；挂角色上（1:1），多角色并集 | "他能看多广" | `sys_data_scope`（5 类型） |
| **权限** | 能力门禁；挂角色上 | "他能进哪扇系统门" | `sys_permission`（4 真开关）/ `sys_role_permission` |

## 二、关系图（定版）

```
        ┌─────────── 档案面（单数，HR事实）───────────┐
        │  主部门(1) + 兼职部门(N) + 主岗(1) + 主管(1)  │
        └──────────────────┬───────────────────────┘
                           │ 成员(N)  ←—— 授权唯一入口（sys_user_role）
                           ▼
        ┌─────────── 授权面（复数，可多份）────────────┐
        │  角色：权限(并集) + 数据范围(并集) + 角色名    │
        └──────────────────┬───────────────────────┘
                           │
     部门树 ──锚定──> 范围计算   角色名 <──流程节点指派（逐字匹配）
```

## 三、六个业务问题由谁回答（决策表）

| 你问的问题 | 谁回答 | 其余概念参与吗 |
|---|---|---|
| 这张单是谁的？ | **部门**（提交人主部门） | 不参与 |
| 这张单在谁的列表里出现？ | **数据范围**（角色的，并集 + 本人单据基线） | 部门当计算原料 |
| 这个审批节点谁能按同意？ | **角色名**（节点指派，逐字匹配） | 其余全不参与 |
| 这个人能进管理后台/提交单据吗？ | **权限**（4 真开关） | 不参与 |
| 这个人是干哪行的？ | **岗位**（纯档案） | 不参与 |
| 这个人该在哪个角色里加/删？ | **成员**（唯一授权动作） | —— |

**角色表的老大是"角色名"列**：OA 审批唯一读取的字段（流程节点写角色名字符串，部署为候选组，逐字匹配）。系统三层保护：全局唯一、改名级联同步流程节点、候选组与角色名逐字一致的契约警告。建角色名要像起身份证号一样谨慎：用稳定职能名，不带人名/部门名/序号。

## 四、跨角色/跨部门/跨岗位人员的处理（定版）

以翁婷婷为标本（会计主管&内控[财务中心] + 出纳[资管中心]）：

| "跨" | 处理方式 | 判定 |
|---|---|---|
| 跨角色 | 多成员关系并集生效；加面=加成员，撤面=摘成员，全程不动档案 | ✅ 核心机制 |
| 跨部门 | 主部门(1)+兼职部门(N) 表达；审批路由无部门维度 | ✅ |
| 跨岗位 | 单主岗字段 + 各角色自带适用岗位 | ✅ 单主岗为行业惯例 |

**原理**：人的档案只记锚点事实（单数），全部多面性由角色承载（复数）。反面检验：若挂角色吸收角色的部门，出纳面的范围锚点会被会计主管面搅乱——唯一自洽的结构。

**原型数据依据**：原型无人员档案（人员身份=成员列名字的集合）；但其负责人范围文案"所属中心单据"只有锚定人员各自部门才可计算——人员级部门是原型数据隐藏的必需依赖，非我们加戏。

## 五、四条铁律（全行业收敛点，无流派分歧）

1. **授权只认成员关系**——部门/岗位是档案，永不参与授权判断
2. **多面人必有主锚点**——主部门/主职/主雇佣，无一家例外
3. **层级住在流程里**——审批认节点指派的名单，角色表里没有老大；唯一特权是超级管理员角色的 `APPROVE_ALL_NODES`（代审任意节点）
4. **权限种类预置只读、分配可管**——没有主流产品开放"界面造权限"（无代码校验的权限是安慰剂）

## 六、主流对比

| 概念 | 钉钉/飞书 | 传统 OA（泛微/致远） | Workday/SAP | **我们** |
|---|---|---|---|---|
| 部门 | 树+多挂+主部门 | 分部/部门树 | 管理组织树 | 树+主(1)兼(N) |
| 岗位 | 单职位文本 | 岗位挂部门（矩阵） | Position 编制占用 | 全局职种库+单主岗 |
| 角色 | 扁平名单，与部门解耦 | 角色（可带部门） | 角色权限 | 扁平+归属部门（纯描述） |
| 数据范围 | 管理范围（全部/指定部门） | 数据权限（本部/含子/全部） | 角色安全域 | 5 类型挂角色+并集 |
| 权限 | 平台预置只选不造 | 功能+流程权限 | 预置权限点 | 4 真开关预置只读 |
| 成员 | 人↔角色多对多 | 人↔角色多对多 | 人↔Position 雇佣 | 人↔角色多对多 |

四派在四条铁律上零分歧；我们站在协同派位置，与钉钉/飞书逐项同构。

**数据范围 5 类型的分工**：
```
ALL            全部（公司级视野）
OWN            仅本人（基线之上最紧）
DEPT           本部门（锚人员主部门，管理型）
DEPT_AND_CHILD 本部门及以下（闭包子树，中心负责人用）
CUSTOM         自定义部门集合（共享职能角色用——核算会计"按业务部门分配"的本意）
```

## 八、配置铁律（照做即所见即所得）

```
"我的领导审我"        → 直属主管节点 + 员工挂汇报线（勿建跨部门大角色）
"出纳/法务/用印"等职能 → 角色节点，成员全公司集中
"提交单据"            → 角色勾 可提交单据
"进管理后台"          → 角色勾 配置流程与权限
"看多广"              → 角色的数据范围类型（职能服务型用 CUSTOM 勾服务对象）
"谁能审某节点"        → 节点上写角色名（角色存在性有保存校验）
```
