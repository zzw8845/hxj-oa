## Context

当前项目为空的 Maven 项目（Java 17，`pom.xml` 无依赖，仅有 Hello World 的 `Main.java`）。业务需求已由高保真 HTML 原型（`海峡金OA审批系统0827.html`）完整表达，并已固化为 8 个能力规范（见 `specs/`）。本设计基于原型与规范，确定从零实现**后端 API 服务**的技术方案。前端不开发，由后续独立项目或第三方对接。

## Goals / Non-Goals

**Goals:**
- 后端提供完整 REST API，数据库持久化，支持认证、单据、流程、审批、角色权限、用印、归档、统计看板
- 数据库采用 MySQL
- 审批流采用主流工作流引擎 Flowable
- 提供 OpenAPI 接口文档，供前端或其他系统对接
- 数据模型覆盖原型中的全部业务实体（单据、流程、角色、人员、审批记录、附件、抄送、归档）

**Non-Goals:**
- 不开发前端页面（登录页、业务页面等），仅提供 API
- 不实现消息通知（邮件/短信/IM 推送），原型中仅 UI 暗示，后续迭代
- 不实现多租户/集团级部署，仅面向海峡金单一组织

## 原型详细需求清单

以下为从原型 `海峡金OA审批系统0827.html` 中提取的全部业务需求，作为实现依据：

### 1. 单据体系
- **三类业务单据**：日常付款（含报销类项目）、业务付款、用印申请；展示映射：日常付款→日常申请单、业务付款→付款申请单、用印申请→用印申请单
- **单据字段**：编号、所属公司（海峡金/海峡金供应链）、对应项目、申请人、部门、金额、简易发票明细、申请事由、当前节点、状态、前置关联（报销按单据编号/业务付款按合同编号）、付款后需补材料标记、关联合同编号
- **附件清单规则**：按业务类型生成必传附件项（报销类：关联前置单据/发票及费用明细/付款截图或行程凭证；供应商付款类：关联前置单据/原始明细账单/对账单/发票；其他：关联前置单据/业务证明资料/发票/收款信息；用印类：用印文件附件）
- **用印申请字段**：用印项目、用印部门、用印时间、用印文件名称、用章类型（公章/合同章/法人章/财务专用章/发票专用章）、用印原因；金额不适用
- **单据编号**：类型前缀 + yyyyMMdd + 当日流水号（如 FK202608260031），提交后不可修改
- **单据分类规则**：申请事项含"合作方退款/服务费结算/闭店/退店" → 业务付款，其余 → 日常付款
- **状态机**：待审批 → 审批中 → 已通过 / 已驳回
- **前置单据关联**：报销关联差旅前置申请、付款关联合同审批，审批人可查看全部前置资料
- **再次提交**：复制历史单据信息生成新编号（原型最终版工作台入口调整为"详情"，API 能力保留）
- **发起人自选抄送**：费用预算、公司发文等流程支持提交时自选抄送人
- **快捷单据目录**：日常付款 37 项、业务付款 9 项、用印申请 3 项

### 2. 审批流程（20 条预置流程）
1. 闭店（入驻店销和代销）：发起人 → 条件分支 → 直属主管 → 商务专员/运营服务主管 → 执行总经理/公司领导 → 会计主管&内控 → 出纳 → 抄送相关负责人
2. 采购申请：发起人 → 直属主管 → 采购询价 → 行政主管（按需）→ 会计主管&内控 → 执行总经理（≥2万元）→ 采购办理 → 发起人签收
3. 低值易耗品（含办公物品）领用：发起人 → 直属主管 → 行政专员发放 → 发起人签收
4. 非标合同审批及用印：发起人 → 直属主管 → 会计主管&内控（涉及资金）→ 法务 → 法务主管 → 公司领导（涉及资金）→ 内控专员用印 → 发起人上传归档附件
5. 费用报销：发起人 → 直属主管 → 会计（按部门）→ 会计主管&内控 → 公司领导（大额）→ 出纳 → 抄送相关负责人
6. 费用预算：发起人 → 直属主管 → 会计主管&内控 → 发起人自选抄送
7. 应付款申请：发起人 → 直属主管 → 会计（按部门）→ 会计主管&内控 → 公司领导（大额）→ 出纳 → 抄送相关负责人
8. 公司发文申请：发起人 → 逐级主管 → 法务 → 内控主管 → 执行总经理 → 行政专员编号发文 → 发起人自选抄送
9. 固定资产报废报损：发起人 → 资产归属部门确认 → 财务经理 → 执行总经理 → 资产管理员办理 → 抄送管理人员
10. 固定资产调拨：发起人 → 调出部门确认 → 调入部门确认 → 调出/调入资产管理员办理 → 抄送财务及内控
11. 固定资产入库：发起人 → 直属主管 → 行政专员入库登记 → 抄送财务经理
12. 黄金业务开户：发起人 → 公司领导 → 抄送内控及内控主管 → 发起人办理 → 抄送总经办/法务/商务
13. 借款申请：发起人 → 直属主管 → 会计主管&内控 → 会计处理 → 出纳付款并上传回单 → 抄送财务及公司领导
14. 客户交易手续费调整：发起人 → 执行总经理 → 抄送财务/内控/法务/运营服务
15. 客户结算服务费：发起人 → 会计（按业务类型）→ 财务经理/内控主管/财务总监 → 会计主管&内控 → 出纳或商务对账 → 抄送相关负责人
16. 提货人新增或变更：发起人 → 交付主管 → 抄送内控主管及总经办
17. 通用审批申请：发起人 → 逐级主管 → 会计主管&内控（涉及资金）/执行总经理 → 抄送总经办
18. 业务招待申请：发起人 → 直属主管 → 会计主管&内控 → 执行总经理 → 抄送总经办
19. 银行账户管理调整：发起人 → 公司领导 → 出纳确认 → 内控主管 → 抄送财务/法务/商务
20. 用印及证照申请：发起人 → 直属主管 → 条件分支 → 运营服务主管/会计 → 会计主管&内控 → 财务经理 → 公司领导 → 内控专员用印或领取证照 → 发起人归还/商务归档 → 抄送内控主管

### 3. 审批操作
- **通过审批**：上传当前节点凭证（必填）+ 审批意见，末节点通过后完结归档
- **指定层级驳回**：驳回至提交人/直属部门负责人/核算会计/内控合规/出纳，原因必填，可选填需要补充的材料
- **通过但补材料**：付款前补充（补完跳过当前审批人进入下一节点）/ 付款后补充（未补齐不可闭环）
- **加签**：邀请其他人员参与审核，加签人员必选
- **审批留痕**：记录操作人、操作类型、操作时间、审批意见、上传凭证
- **审批权限校验**：仅当前节点审批人或超管可操作
- **流程透明度**：审批人可查看全部前置节点信息、历史意见、附件

### 4. 角色权限（19 个预置角色）
超级管理员、公司领导、执行总经理、一级中心负责人、二级部门负责人、会计主管&内控、核算会计、内控主管、内控专员、法务、法务主管、行政专员、行政主管、商务专员、运营服务主管、交付主管、财务经理、出纳主管、出纳

每个角色含：对应部门、岗位、数据范围（本人单据/本部门单据/全公司财务单据/全公司业务单据/全部部门与全部节点）、权限点、成员列表。人员只分配角色，权限由角色继承。

### 5. 用印管理
- 用印申请独立条线，按业务类型（非标合同审批及用印/通用审批申请/用印及证照申请）匹配预置流程配置流转，末端含用印办理与盖章文件归档环节
- 用章类型：公章、合同章、法人章、财务专用章、发票专用章
- 用印凭证归档：发起人回传盖章文件后流程完结，未回传不可完结

### 6. 归档台账
- 仅归档审批通过的单据
- 多条件组合查询：申请人、申请部门、单据编号、归档时间范围
- 台账导出（Excel/CSV）

### 7. 统计看板与风险预警
- 首页统计：已驳回、待我审批、本月已办结数量及环比、流程合规率、菜单角标数量
- 首页待办列表：按临近超时优先排序
- 工作看板：申请总量、审批中、已办结、平均审批时长、节点处理效率、单据状态分布
- 近7天流程趋势：每日发起/办结数量、状态分布
- 风险预警：金额 ≥ 8 万元标记为风险单据

## Decisions

### 1. 后端框架：Spring Boot 3.x + Java 17
- **选择**：Spring Boot 3.2 + Spring Web + Spring Data JPA + Spring Security + JWT
- **理由**：项目已用 Java 17；Spring Boot 生态成熟，JPA 可快速建模；Spring Security 提供认证与授权基础
- **备选**：Quarkus（更轻量但生态相对小）、Node.js/NestJS（与现有 Java 项目不一致）

### 2. 数据库：MySQL 8.x
- **选择**：MySQL 8.x 为主库，开发/测试环境可用 H2 兼容模式或本地 MySQL
- **理由**：用户明确要求 MySQL；MySQL 8 支持 JSON 类型、事务可靠、国内部署普及
- **备选**：PostgreSQL（JSON 支持更强，但用户已指定 MySQL）

### 3. 审批流引擎：Flowable 7.x
- **选择**：Flowable 7 工作流引擎，BPMN 2.0 流程定义 + 流程实例执行
- **理由**：用户要求"审批流参考主流方案"；Flowable 是主流开源工作流引擎，支持 BPMN 2.0、任务分配、条件网关、会签/或签、历史留痕，与 Spring Boot 集成成熟
- **备选**：Activiti 7（社区活跃度较低）、Camunda 8（云原生但部署较重）、自研轻量引擎（能力有限）

### 4. 认证方案：JWT + Spring Security
- **选择**：无状态 JWT（Access Token），登录接口返回 token，前端存储并随请求携带
- **理由**：前后端分离场景标准方案，无状态便于水平扩展
- **备选**：Session + Cookie（需处理跨域与 CSRF，前后端分离下较繁琐）

### 5. 权限模型：RBAC（角色-权限-数据范围）
- **选择**：用户 → 角色 → 权限点 + 数据范围；权限点与数据范围在角色上配置，用户仅分配角色
- **理由**：与原型"人员只分配角色，权限由角色继承"完全一致
- **备选**：直接给用户配权限（与原型设计冲突，不采用）

### 6. 附件存储：本地文件系统 + 数据库元数据
- **选择**：附件文件存本地磁盘目录，数据库存文件元数据（文件名、路径、上传人、所属节点）
- **理由**：内网部署场景简单可靠；后续可平滑迁移到对象存储
- **备选**：直接存数据库 BLOB（不利于大文件与备份）、对象存储（需额外基础设施）

### 7. 单据编号：数据库序列 + 日期前缀
- **选择**：编号 = 类型前缀 + yyyyMMdd + 当日流水号（流水号由数据库序列/计数保证唯一）
- **理由**：与原型编号格式一致，可读性强；数据库层保证并发唯一

### 8. 接口文档：SpringDoc OpenAPI
- **选择**：SpringDoc OpenAPI 3 自动生成接口文档，提供 Swagger UI
- **理由**：前端不开发，接口文档是对接方的核心交付物
- **备选**：手动维护 Markdown 文档（易过期）、Knife4j（增强 UI，但依赖 SpringDoc 基础）

## Risks / Trade-offs

- [Flowable 学习与配置成本] → 仅使用线性节点链 + 条件网关（排他网关）子集，封装为审批服务，业务层不直接暴露 Flowable 概念
- [Flowable 与业务单据解耦] → 业务单据表存 `process_instance_id`，Flowable 变量存 `document_id`，通过统一服务封装
- [JWT 无法服务端吊销] → 员工离职/角色变更后旧 token 仍有效至过期。缓解：token 有效期设短（Access Token 4 小时 / Refresh Token 7 天），角色变更时前端重新登录；已实现 Token 黑名单（`TokenBlacklistService`，退出登录时立即失效）
- [本地文件存储扩展性] → 单机磁盘容量有限。缓解：文件路径可配置，预留对象存储抽象接口
- [金额分级审批阈值等业务规则未完全明确] → 条件分支阈值（如 ≥2 万元）在流程定义中可配置化，避免硬编码
- [MySQL JSON 类型兼容性] → 仅将流程配置、权限点集合等少量字段用 JSON，核心业务字段保持关系型建模

## Migration Plan

1. 后端：搭建 Spring Boot 骨架 → 数据模型与 JPA 实体 → 认证模块 → 单据/流程/审批/角色/归档/统计 API → 单元测试
2. 审批流：集成 Flowable → 定义 BPMN 流程模板 → 流程服务封装 → 审批操作对接
3. 数据初始化：Flyway 迁移脚本 + 种子数据（角色、流程配置、快捷目录、示例人员）
4. 部署：单机部署（后端 jar + MySQL），Nginx 反代
5. 回滚：数据库迁移脚本可回滚；后端 jar 保留上一版本

## Open Questions

- 是否需要"保存草稿"能力？原型有按钮但无逻辑 —— 首版可先不做，后续迭代
